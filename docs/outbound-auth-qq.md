## 发件代码审查结论

`src/mail_control.py` 的自定义发件由合法前缀与本站已有域名组成地址，邮件头 `From` 和传给 `smtp.send_message(..., from_addr=sender, ...)` 的信封发件人使用同一 `sender`。API 发件使用请求 `from` 或 API 默认发件人，并要求该地址为已启用邮箱，最终进入相同发送函数。未发现这两条应用路径自行造成 `From` 与信封域错配的代码。

但是，“域名已在 Mailu 中创建”并不等于公网 DNS 已具备对应出口的发件授权。实际出站身份仍需结合 Postfix 队列、可能的信封改写以及最终公网出口核对。仅修改 `Reply-To` 或手工添加 `Return-Path` 不能作为此次 SPF 问题的修复验收。

应用当前在本地 SMTP 接受后返回 `sent=True`，API 发送日志也在此时记为 sent。这只能说明本机 SMTP 已接收，不等同于 QQ 等外部收件方最终接收；后续队列退信需要另行跟踪。本文不修改该行为。

## 建议调整与验收边界

1. SPF 保留现有 `mx`、`a:postal.qnns.de` 与 `~all` 机制，并显式加入真实出口 IP。建议将唯一 SPF TXT 调整为 `v=spf1 ip4:104.223.85.78 mx a:postal.qnns.de ~all`，不要另建第二条 SPF 记录，不改 MX、网站解析或其他业务的 DNS。当前记录本已通过 a 机制授权该 IP，此调整用于显式表达出口，并非已证实的根因修复。
2. 在拥有 DNS 管理入口后，按真实使用的选择器和预期策略整理旧 DKIM 与重复 DMARC；保留当前服务器正在使用的公钥及必要发送渠道。
3. 在机房或 IP 提供方控制台处理 PTR，按现用 HELO `postal.qnns.de` 核对正反向一致性；不将其完成视为 QQ SPF 已修复。
4. 变更后复查权威及递归 DNS，再以同一发件域向 QQ 进行一次受控重试，记录新的信封发件人、源 IP、队列 ID 和 QQ 最终 SMTP 响应。只有 QQ 实际接收并在收件侧确认，才可填写该场景通过；本机队列 accepted、其他接收方 pass 或网页显示发送成功均不能替代。
